# ARCHITECTURE: что страхует от переписывания, а что нет

Дата: 2026-09-22. Статус: зафиксировано по итогам ревью; структура уточнена 2026-10-12. Метод:
FSD-слои (`app → pages → widgets → features → entities`, `shared` снизу; в `widgets` —
самодостаточные оверлеи страницы (панель, шторка, карточка) — см. §Внутренняя структура).

## Что реально страхует (проверено, а не заявлено)

1. **Слои с правилом «импорт только вниз».** Новая фича = новый слайс в `features/` + при
   необходимости виджет; существующие слайсы не трогаем. Пример: роллер уже живёт в
   `features/tableRoll/`, новая фича (пул) ляжет отдельным слайсом рядом — viewer-grid его не
   заметит.
2. **TypeScript strict + `noUnusedLocals` + ESLint.** Переименование функции или смена сигнатуры —
   компилятор находит все использования. Это главная механическая страховка рефакторинга.
3. **Тесты чистой логики (Vitest, `npm test`).** Стор `entities/rollHistory` покрыт: лимит и
   персист, битый JSON и quota не роняют стор, подписки, разбивка пула; реестр `entities/dieModel` —
   уникальность id и ссылки `DEFAULT_SELECTED`. Правило: вся новая логика без DOM — сразу с тестом
   рядом (`*.test.ts`).
4. **ES-модули + Vite.** Ленивый `dynamic import()` работает из коробки — физика (`cannon-es`) и
   будущие экраны подгрузятся по требованию, главный бандл не распухнет.
5. **Хуки качества.** Prettier + markdownlint + ESLint на pre-commit: архитектурный дрейф виден в
   диффе, а не через полгода.

## Что НЕ застраховано (честные границы)

1. **Мульти-рендерер.** Сейчас 1 панель = 1 WebGL-контекст (см. PERF.md §2). Экран броска с физикой
   — другая сцена и другой цикл; `viewer-grid` будет эволюционировать. Это не «переписать всё», а
   заменить/расширить слайсы — именно для этого FSD.
2. **Ручной UI без фреймворка.** Формы/валидация/сложные списки придётся писать руками. Триггер
   пересмотра — в STACK.md (комнаты, аккаунты, стейт >~500 строк).
3. **Глобальный CSS без скоупов.** Классы плоские, коллизии возможны. Правило: префиксы по слайсу
   (`model*`, `viewer*`); при росте — CSS-модули или scope. Пока хватает дисциплины + Prettier.
4. **DOM-зависимый код нетестируем Vitest без jsdom.** Тестируем только чистую логику; UI проверяем
   Playwright-скриптами (как сейчас).

## Куда класть новый код (шпаргалка)

| Что добавляем                                                                         | Куда                             |
| ------------------------------------------------------------------------------------- | -------------------------------- |
| Новый экран/режим                                                                     | `pages/<name>/`                  |
| Самодостаточный блок UI (панель настроек, шторка, карточка)                           | `widgets/<name>/`                |
| Экранное представление, зависящее от контекста экрана                                 | в `pages/<name>/` (см. ниже)     |
| Действие/стейт (бросок, пресеты)                                                      | `features/<name>/` + `*.test.ts` |
| Данные (модели, скины, словарь)                                                       | `entities/<name>/`               |
| Переиспользуемое (three-фабрики, парсер нотации)                                      | `shared/`                        |
| Низкоуровневая механика костей (физика, чтение результата, звук, ориентация, `DieId`) | `shared/dice/`                   |
| Точка входа, глобальные стили                                                         | `app/`                           |

Слой `widgets` (решение 2026-10-12): все 6 слоёв FSD объявлены всегда
(`app, pages, widgets, features, entities, shared`). Критерий «виджет или содержимое страницы» (FSD
v2.1, Layers → Widgets): самодостаточный оверлей, живущий целиком и нигде не переиспользуемый вне
одной страницы, — содержимое страницы; блок, который по структуре остаётся самостоятельным (у него
свой стейт-контракт и он не сращен с композицией экрана), — `widgets`. На практике: панель настроек
(`widgets/drawer`), шторка пресетов (`widgets/sheet`), карточка музыки (`widgets/musicCard`) —
разнесены 2026-10-12; кандидаты дальше — viewer-grid, вторая страница. Композиция экрана
(`MobileTable`, `Head`/`Foot`/`Hint`, движок) остаётся в `pages/HomePage`.

Двери (решение 2026-10-12): у каждого слоя свой `index.ts` — внешний импорт идёт в дверь слоя
(`@/features`, `@/entities`, `@/pages`, `@/widgets`, `@/shared`, `@/app`). Двери слайсов/сегментов
(`@/features/tableSetup`, `@/shared/dice`, `pages/HomePage/index.ts`) остаются для внутренних
связей: слой-баррели реэкспортуют их, а кросс-сегментные импорты внутри shared ходят в сегментную
дверь (импорт в дверь своего слоя — цикл, no-circular). Внутри слайса — относительные пути. Правила
`fsd/public-api` + `fsd/no-public-api-sidestep` в steiger следят за дверями слайсов;
`fsd/no-layer-public-api` и `fsd/no-segmentless-slices` выключены осознанно; dep-cruiser держит
down-only и отсутствие циклов.

Внутренняя структура (решение 2026-10-12):

- **entities / features — плоские**: файлы в корне слайса (вложенность вида
  `dieModel/model/models.ts` избыточна).
- **widgets — три самодостаточных слайса-оверлея** (разнесение 2026-10-12): `drawer/` (панель
  настроек: 8 файлов), `sheet/` (шторка пресетов + `Chip`/`useChipHold`), `musicCard/` (карточка
  музыки); у каждого дверь `index.ts`. Прямых импортов между ними нет — связь только через
  features-стейт и shared-кит. Общая шапка оверлея (`OverlayHead`) и кит стилей (`overlay.stylex`,
  `mt.stylex`) — в `shared/ui` (презентация без бизнеса, общая для трёх слайсов), `useDirtyPanel` —
  в `features/tableUi`, `useSoundToggle` — в `features/sound` (владельцы стейта, который диспатчат).
- **pages — композиция экрана** (решение 2026-10-12 после ресёрча FSD v2.1): канон
  (<https://feature-sliced.design/docs/reference/layers#widgets>) различает «составляющее большую
  часть страницы и сращённое с ней» (содержимое страницы) и самодостаточные блоки (виджеты);
  `HomePage` был 12-строчной обёрткой, слой `widgets` — одним потребителем («You don't have to use
  every layer»). В `pages/HomePage/` остаются: `ui/` (контейнер `MobileTable`, `Head/`, `Foot`,
  `Hint`, `Live`, `Backdrop`, `Watermark/`, `Toast`, `useToast` — экранные представления со связью
  на data-phase/движок), `model/` (движок, жесты, раскладка, `throwPack`, `useTableEngine`,
  `selectors.ts` — только экранный `selectPhase`, DOM-контракт `data-phase` для e2e); дверь слайса —
  `index.ts`. Селекторы стейта живут рядом со своими редьюсерами (`features/*/selectors.ts`,
  `entities/rollHistory/selectors.ts`), форматтеры — у владельца типа
  (`features/tableSetup/format.ts`, `entities/rollHistory/format.ts`); сегмент `lib/` упразднён. В
  `ui/` (2026-10-12) — папки компонентов со всем их атомом, **у каждой папки-компонента своя дверь
  `index.ts`** (потребитель импортирует папку `./Head`, а не файл `./Head/Head` — импорты без шума;
  двери не плодятся только в служебных сегментах `model/`); одиночные компоненты — плоско в корне
  `ui/` (дверь — `index.ts` слайса). Обоснование и цитаты спеки — в скилле
  `.opencode/skills/fsd-review/SKILL.md` (§Канон/Обоснование структуры).
- **shared** — сегменты `dice/ui/three/arena/api`, у каждого `index.ts` (public API); сегмент `lib`
  — тестовые хелперы (`pumpUntilSettled`), только для `*.test.ts` и намеренно мимо двери слоя; дверь
  слоя `shared/index.ts` реэкспортит всё, кроме `api` (msw — только динамический импорт из
  `main.tsx`).
- **app** — `index.ts` (store + hooks) как дверь; `main.tsx` — точка входа.

Файлы компонентов — PascalCase (`Head.tsx`, `DrawerPowerSection.tsx`); утилиты и файлы модулей —
camelCase (`engine.ts`, `format.ts`).

Запрещено: импорты вверх по слоям и между слайсами entities/features; компоненты страницы общаются
через `features/`-стор.
