# Ресерч: CAD-стек vs нейрогенерация — что выгоднее для качества

Дата: 2026-09-20 (обновлено 2026-09-21 — набор d4–d20 на OpenSCAD) Контекст: сборка D6 16×16×16 мм
(фаска/скругление r=1, 21 пипс) в трёх CAD и сравнение с AI-генерацией 3D; затем полный набор
d4–d20.

## Резюме (TL;DR)

Для **точного игрового кубика** классический CAD выигрывает по всем статьям качества: размеры
гарантированы (16.0×16.0×16.0 мм, проверено по BoundBox), топология чистая, есть STEP/FCStd для
производства и повторных итераций. Из CAD стеков **OpenSCAD дал лучший баланс**: самый короткий код
(60 строк), самый быстрый рендер (секунды после замены minkowski на hull), гладкие скругления, ноль
скрытых багов ядра. FreeCAD и CadQuery дали тот же результат, но ценой обхода нескольких багов
OCC/инструментов.

**Набор d4–d20 подтвердил выбор OpenSCAD**: после перехода с 2021.01 (CGAL) на снапшот 2026.09.18
(Manifold) все 6 костей — d4 с цифрами на вершинах, d6/d8/ d4/d6/d8/d10/d12/d20 с цифрами (d10: 0–9,
у 6/9 подчёркивания) — рендерятся за 0.3–2 с каждая (против 95+ с в 2021.01). Проблем с полиэдрами
не осталось: d12 и d20 дали корректную раскладку противоположных граней N+1 без единого ручного
вмешательства.

**Нейрогенерация (Hunyuan3D-2, TRELLIS, Meshy, Tripo) для кубика невыгодна**: нет контроля размеров
(проблема честности броска), сырые меши 30-100к+ треугольников с не-манифолдной топологией, нужен
ремеш/децимейшн, нет STEP и параметричности. Выигрыш только в одном: скорость получения
«художественного» прототипа по картинке — если кубик нужен декоративный, а не игровой.

## 1. Эмпирика проекта (что реально измерено)

### FreeCAD 1.1.3 + Robust MCP (83 инструмента)

- Габариты: **16.0×16.0×16.0 мм** (проверено BoundBox финального тела)
- Выход: STEP + STL + FCStd (проект открывается в GUI)
- Меш при tolerance 0.01: 187 070 треугольников
- Найденные баги (реальные, в проде):
  - `Part::Box` занимает 0..16, а не −8..8 — пипсы ложились в углы граней
  - `boolean_operation` создаёт новый объект на каждый вырез — экспортировался только первый пипс
    («кубик с 1 точкой»)
  - `chamfer_edges` падает без явного списка рёбер; `export_stl` сломан (IndexError в мосте) —
    экспорт через нативный `Shape.exportStl`
- Вывод: мощно, но на каждый шаг — баг-хантинг.

### OpenSCAD 2021.01 → 2026.09.18 (Manifold)

- Код: `tools/d6.scad` (60 строк) и `tools/dice_set.scad` (параметрический набор)
- Рендер: секунды (после замены `minkowski` на `hull()` из 8 сфер — minkowski зависал на 5+ минут)
- Меш: 22 044 треугольника ($fn=64 на скруглении)
- Гладкие радиусы рёбер — по субъективной оценке «самый красивый кубик»
- **Ключевой урок для набора**: CGAL в 2021.01 делал hull из 8 сфер за 58 с, а полный d6 с пипсами —
  95 с; d20 с 210 пипсами просто не влезал в таймаут. Manifold в снапшоте 2026.09.18 делает d20 за 2
  с и весь набор — за ~7 с.
- Обнаруженные и исправленные баги генератора:
  - Разные полиэдры имели разный «радиус вершин» при одинаковом SIZE → у d8/d10 пипсы не прорезались
    (плоскости граней не совпадали с уровнем пипсов). Решение: нормировка
    `verts = unit_verts / die_inradius` — все плоскости граней ложатся на 8.0 от центра.
  - У d4 нормали граней смотрели внутрь (обмотка TETRA_F) → гравировка уходила в центр кости.
    Решение: `face_normal()` всегда ориентирует нормаль наружу.
  - Свой `d10` (10 вершин, «кайты» без полюсов) давал некомпланарные грани; заменил на полярный дуал
    правильной антипризмы (12 вершин, 10 плоских кайтов) — все грани плоские, противоположные пары
    сходятся.
  - Раскладка значений была последовательной (1..N по порядку граней) → противоположные грани не
    давали N+1 (d20 дублировал «1», терял «20»). Решение: таблицы `opposite()` для d6/d8/d12/d20 +
    d10 (0-9, сумма 9).
  - `layout_for(0)` для d10 с отрицательным индексом массива давал 6 пипсов на «0» (в OpenSCAD
    `list[-1]` — последний элемент); добавил явный `v==0 → []`.
  - Текст в headless: fontconfig не находил шрифты → `text()` рендерил пусто/криво; лечится
    `FONTCONFIG_FILE=.../fonts/fonts.conf` с путём к Liberation TTFs.
  - Масштаб гравировки: координаты граней нормированы (inradius=1), а тело масштабируется
    `SIZE/2-EDGE_R=7` — цифры надо умножать на тот же масштаб.
- Вывод: 2021.01 для полиэдров набора непригоден по скорости; свежий снапшот с Manifold — идеален.
  Ограничение прежнее: только STL, нет STEP/FCStd.

### CadQuery 2.8.0

- Код: `tools/d6_cadquery.py`, экспорт STEP + STL
- Меш: 75 883 треугольника
- Найденные баги OCC (4 шт!):
  - `Solid.makeSphere()` создаёт **полусферу** (angleDegrees2=90) — «обрезка полусферами»
  - `Workplane.translate()` **не двигает солиды** — все 21 сферы резали центр куба
  - Boolean cut сферой в отрицательной полуоси — невалидное тело
  - Шов сферы должен быть перпендикулярен оси грани (рабочая плоскость выбирается по грани: X-грань
    → 'YZ', Y → 'XZ', Z → 'XY')
- Вывод: API приятный, но ядро (OCCT через cadquery-ocp 7.9.3) капризное.

### Общий пайплайн web-качества

- STL → GLB: Blender headless (`blender-stl-colorize.py` — куб, `blender-stl-colorize-set.py` —
  любой полиэдр) — материалы + коррекция нормалей (у CadQuery впадины экспортировались с нормалями
  внутрь → чёрный рендер)
- Цветовая разметка набора: пипсы = поверхности сфер-пипсов (расстояние до бокса цифры на плоскости
  грани и ниже её уровня (`DIGIT_DEPTH = 0.5 мм` — минимум для читаемости на FDM-печати) (выпуклое
  тело, минимум поверхности = плоскость грани на 8.0)
- Просмотр: three.js, 3 панели (сравнение CAD) + 6 панелей (набор d4–d20), автоповорот, drag&drop

## 2. Нейрогенерация 3D: срез рынка 2026

| Модель                 | Ввод                  | Скорость                | Сильные стороны                                                | Ограничения                         |
| ---------------------- | --------------------- | ----------------------- | -------------------------------------------------------------- | ----------------------------------- |
| Hunyuan3D 3.5/Pro      | текст/1-8 изображений | 2-6 мин                 | до 8K PBR, face count 40K-1.5M                                 | платно, гео-ограничения open-source |
| TRELLIS 2              | 1 изображение         | 1-3 мин (локально ~30с) | фотореализм, 512³-1536³ воксели, MIT                           | нужен Linux + 24GB GPU              |
| Tripo H3.1 / SmartMesh | текст/изображения     | ~10-60с                 | чистая низкополигональная топология (Smart Mesh P1.0), риггинг | закрытый SaaS                       |
| Meshy 7                | текст/изображения     | ~30-60с                 | «водонепроницаемые» меши для 3D-печати, автопочинка            | закрытый, текстуры «плоские»        |

Ключевые высечки 2026 (по независимым сравнениям):

- **«Pretty ≠ printable»**: большинство AI-мешей выходят не-манифолдными, с дырами; починка в
  Blender/Meshmixer занимает больше времени, чем сэкономила генерация (Meshy — единственный с
  встроенной печатной подготовкой).
- Бенчмарк геометрии Meshy 7 vs Tripo 3.1 (single-view): совпадение формы 81% vs 79%, поверхностные
  детали 59.8% vs 51.7% — т.е. даже лидеры **не гарантируют геометрию**, не говоря о миллиметровых
  размерах.
- Современные лидеры ориентированы на: геймдев-ассеты (текстуры/риггинг), фотореализм (TRELLIS),
  печать (Meshy) — но НЕ на размерную точность.

## 4. Вердикт

1. **Для игрового кубика (качество):** CAD. Лучший баланс — **OpenSCAD**: минимальный код,
   мгновенные итерации, гладкая геометрия, детерминированный результат. FreeCAD — если нужен
   STEP/FCStd и GUI-правка. CadQuery — если важен Python-код, но готовы к багам OCC.
2. **Решение «один CAD или три» (2026-09-21):** основной генератор набора — **OpenSCAD** (снапшот
   2026.09.18, Manifold). На d12/d20 — самых сложных полиэдрах с филе и пипсами — ни FreeCAD, ни
   CadQuery не показали преимуществ: их MCP/API требуют обходов багов на каждый шаг, а результат
   (STL) тот же. FreeCAD остаётся для STEP/FCStd-версии d6 (уже есть) и GUI-правок; CadQuery —
   экспериментальный стенд. Все 6 костей набора живут в одном SCAD-файле.
3. **Нейрогенерация выгодна только как «черновик»** (концепт-арт, декоративные ассеты, неигровые
   фигурки): скорость получения «похожего» объекта за ~1 мин. Для честных игровых кубиков — не
   применима без перестройки в CAD.
4. **Гибридный пайплайн (если захочется нейронки):**
   `AI-генерация (концепт) → ремеш/децимейшн (Blender/Meshy) → параметризация в OpenSCAD/FreeCAD (точные размеры) → STEP/STL → GLB`.
   Нейронка даёт форму и стиль, CAD даёт точность и повторяемость.

## 6. Проверка честности набора (2026-09-22, по STL)

Центр масс (объёмный, по тетраэдрам STL):

| Кость | Объём, мм³ | Смещение CoM от центра, мм |
| ----- | ---------- | -------------------------- |
| d4    | 6979       | 0.0010                     |
| d6    | 4050       | 0.0007                     |
| d8    | 3522       | 0.0004                     |
| d10   | 3237       | 0.0005                     |
| d12   | 2820       | 0.0023                     |
| d20   | 2577       | 0.0019                     |

Смещения 0.0004–0.0023 мм — на два порядка меньше точности FDM-печати (0.1–0.2 мм) и на порядок
меньше допуска прецизионных казино-костей (±0.005 мм на ребро). Вывод: гравировка цифр (0.05–0.1 мм)
баланс не сбивает; как и в казино, при желании можно залить цифры краской той же плотности, что и
тело. Для печатных костей важнее: 100% заполнение, калибровка потока и ориентация печати.
