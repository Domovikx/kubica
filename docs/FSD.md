# FSD (Feature-Sliced Design): слои, слайсы и взаимодействие

Справочный документ по действующей спеке **FSD v2.1** (источник — feature-sliced.design; собрано
2026-10-12). Назначение — один ответ на два вопроса: **какой слой за что отвечает** и **как слои
взаимодействуют**. Здесь — только методология; решения конкретного проекта (kubica) лежат в
`docs/ARCHITECTURE.md`.

## Что такое FSD

Feature-Sliced Design — методология организации фронтенд-кода: набор правил и конвенций, которые
делают проект понятным и стабильным при меняющихся бизнес-требованиях. Это не фреймворк и не
библиотека: ограничений по языку, UI-фреймворку или стейт-менеджеру нет, внедрять можно постепенно
(существующий кодbase мигрируется постепенно: сначала `app`/`shared`, затем UI разносится по
`pages`/`widgets`, затем нарушения правил исправляются).

Три кита методологии:

| Понятие  | Делит код по…               | Назначение                                            |
| -------- | --------------------------- | ----------------------------------------------------- |
| Слои     | уровню ответственности      | стандартизированы во всех проектах, имена фиксированы |
| Слайсы   | предметной области (домену) | навигация: логически связанное живёт рядом            |
| Сегменты | технической природе         | что код делает: UI, данные, бизнес-логика, утилиты    |

Преимущества по спеке: единообразие (одинаковая структура в проектах — быстрый онбординг),
стабильность при рефакторинге (изолированные правки без side-effect-ов), контролируемое
переиспользование (баланс DRY и прагматики), ориентация на бизнес-язык в именовании.

## Иерархия: слои → слайсы → сегменты

```text
Слой (layer)      — уровень ответственности; 6 штук, имена стандартизированы
  └─ Слайс (slice)      — единица предметной области внутри слоя (только в layers entities/
                          features/widgets/pages)
       └─ Сегмент (segment) — группировка по технической природе (ui / model / api / lib / config)

Слои App и Shared — исключение: слайсов нет, сразу сегменты.
```

Ключевые структурные факты:

- Слоёв **6**: `app`, `pages`, `widgets`, `features`, `entities`, `shared`. **Все 6 слоёв заводим
  всегда — даже если какой-то сейчас не используется, он остаётся на будущее.**
- Имена слоёв **стандартизированы**; новые (7-й) слои заводить нельзя.
- Внутри слайса код можно организовывать как угодно — контракт держит public API: «Inside a slice,
  the code could be organized in any way that you want».

## Слои: зона ответственности

Схема (сверху вниз, от наиболее ответственного к базовому):

```text
┌──────────────────────────────────────────────────────────────┐
│ app        — запуск приложения; сегменты без слайсов         │
├──────────────────────────────────────────────────────────────┤
│ pages      — экраны;            слайсы → сегменты           │
├──────────────────────────────────────────────────────────────┤
│ widgets    — крупные самодостаточные блоки UI; слайсы        │
├──────────────────────────────────────────────────────────────┤
│ features   — переиспользуемые действия; слайсы               │
├──────────────────────────────────────────────────────────────┤
│ entities   — предметы бизнес-домена; слайсы                  │
├──────────────────────────────────────────────────────────────┤
│ shared     — переиспользуемая инфраструктура; сегменты       │
└──────────────────────────────────────────────────────────────┘
              стрелка импорта: только ▼ вниз (см. Import rule)
```

Сводная таблица:

| Слой       | Отвечает за                                                   | Типовое содержимое                                     |
| ---------- | ------------------------------------------------------------- | ------------------------------------------------------ |
| `app`      | запуск и склейка приложения                                   | роутер, store, глобальные стили, провайдеры, entry     |
| `pages`    | экраны целиком (или крупные части при nested-роутинге)        | страница со всей её логикой и данными                  |
| `widgets`  | крупные самодостаточные блоки UI                              | панель, модалка-шторка, дашборд, переиспользуемый блок |
| `features` | действия, приносящие ценность пользователю (переиспользуемые) | «бросить кости», «сохранить набор», «войти»            |
| `entities` | предметы реального мира, с которыми работает продукт          | пользователь, кость, история бросков, товар            |
| `shared`   | инфраструктура и переиспользуемые примитивы без бизнеса       | API-клиент, UI-кит, форматтеры, константы              |

### shared — фундамент

Связь с внешним миром (backend, third-party, окружение) и собственные высоко-переиспользуемые
библиотеки. **Слой без слайсов** — только сегменты, и сегменты могут импортировать друг друга
свободно. Типовые сегменты: `api` (клиент и запросы), `ui` (UI-кит, лейауты, «business-themed»
компоненты допустимы, но без бизнес-логики), `lib` (библиотеки с одной зоной фокуса + README, не
свалка `utils`), `config`, `routes`, `i18n`. Свои нестандартные сегменты заводить можно, но имя
должно описывать **назначение**, а не сущность (`components`, `hooks`, `types` — плохие имена).
Бизнес-логики здесь быть не должно.

Особый случай: `shared/ui` и `shared/lib` — коллекции разнородного; одна дверь на всё тянет тяжёлое
в бандл и ломает tree-shaking → отдельный `index.ts` на каждую библиотеку/компонент.

### entities — предметы домена

Слайсы, названные терминами бизнеса (не «компоненты», а «пользователь», «товар»). Внутри: `model`
(схемы, стор, валидация), `api` (запросы к endpoints этой сущности), `ui` (презентация сущности для
переиспользования — необязательно целый блок). Слайсы по умолчанию не знают друг о друга: связи двух
сущностей живут в вышестоящих слоях (features/pages) либо через `@x`-кросс-импорты (только здесь,
минимально).

### features — действия

«Переиспользуемые реализации продуктовых фич» — то, что пользователь **делает**: действия,
приносящие ценность. Ключевой принцип: **не всё нужно делать фичей** — признак нужды:
переиспользуется на нескольких страницах. Внутри: `ui` (форма/кнопка), `model` (состояние и
бизнес-логика действия), `api`, `config`. Слишком много мелких фич топят важные: по приходу в новый
проект функциональность должны читаться из списков `pages` и `features`.

### widgets — крупные блоки UI

Самодостаточные блоки UI. Полезны, когда **переиспользуются на нескольких страницах** или когда
страница состоит из нескольких крупных независимых блоков и этот блок — один из них.

Прямая цитата критерия (Layers → Widgets):

> If a block of UI makes up most of the interesting content on a page, and is never reused, it
> **should not be a widget**, and instead it should be placed directly inside that page.

Допустимо хранить здесь лейауты страниц; при nested-роутинге слой `widgets` может работать как
«полноэкранные роут-блоки» (аналог того, что для плоского роутинга делает `pages`).

### pages — экраны

Одна страница — обычно один слайс; очень похожие страницы (логин/регистрация) можно объединить.
Внутри: `ui` (разметка, loading/error-состояния), `api` (запросы страницы); отдельный `model` для
страницы — редкость, мелкий стейт живёт в компонентах. Явного лимита объёма нет, «as long as your
team still finds it easy to navigate». Нередкий случай: **непереиспользуемый крупный UI-блок
остаётся внутри страницы** — это норма, а не ошибка.

### app — склейка приложения

Роутинг, конфиг стора, глобальные стили, entrypoint, провайдеры, аналитика. Слой без слайсов
(сегменты `routes`/`store`/`styles`/`entrypoint`). Верхний слой: он собирает всё остальное; сам он
не переиспользуется.

## Import rule: как слои взаимодействуют

Правило из спеки (единственная жёсткая стрелка зависимостей):

> A module (file) in a slice can only import other slices when they are located on layers **strictly
> below**.

Что это значит на практике:

- Импорт возможен **только вниз**: `pages` → `widgets` → `features` → `entities` → `shared`.
- Импорт **вверх** (`entities` → `features`) — нарушение.
- Импорт **чужого слайса того же слоя** (`features/a` → `features/b`) — нарушение. Легальная замена
  — подняться на уровень выше или `@x` (только `entities`).
- `app` и `shared` — исключения сами по себе: это «слой = слайс», их сегменты связаны свободно.
- Встраивание (embedding) — например, вставить фичу в другую фичу — происходит **только в
  вышестоящем слое**: «inside a widget, you can import both features and then insert one feature
  into another as props/children». Фича в фичу напрямую — запрещено.

Пример вертикального среза (только импорты вниз):

```text
pages/home/ui/HomePage.tsx
  └─ '@/features/roll-dice'        (действие «бросить»)
       └─ '@/entities/roll-history' (сохранение результата)
            └─ '@/shared/api'       (сетевой слой)
```

Обратная сторона (данные/события «вверх») — не импортами, а композицией: нижние слои ничего не знают
о верхних; верхние передают пропсы/колбэки вниз, состояние читают через стор своего
`model`-сегмента.

## Живое взаимодействие: где что лежит

| Задача                                       | Куда по канону                                          |
| -------------------------------------------- | ------------------------------------------------------- |
| Новый экран / режим                          | слайс в `pages/<name>/`                                 |
| Действие пользователя (кнопка, жест)         | слайс в `features/<name>/`                              |
| Предмет бизнеса (данные, модель, справочник) | слайс в `entities/<name>/`                              |
| Крупный переиспользуемый блок UI             | слайс в `widgets/<name>/` (критерий — выше)             |
| API-клиент, UI-кит, форматтеры, константы    | сегменты `shared/`                                      |
| Роутер, store конфиг, глобальные стили       | сегменты `app/`                                         |
| Лейаут страницы                              | `shared/ui` (простой) или widget/page-слайс (с логикой) |
| Состояние (стор/схемы)                       | `model`-сегмент слайса; конфиг стора — `app/store`      |
| Стили блока                                  | рядом с компонентом (колокализация)                     |
| Запросы к бэкенду                            | `shared/api` или `api`-сегмент слайса                   |

Правила композиции (React-практика из спеки и FAQ):

- Страница собирает виджеты, виджет — фичи и сущности; фичи и сущности «вкладываются» друг в друга
  только руками вышестоящего слоя (через props/children).
- Контейнер владеет данными, презентация — чистые пропсы.
- Общее прикладное состояние (стор) живёт в `model`-сегментах слайсов; провайдер/context — на `app`;
  shared о бизнесе ничего не знает.

## Слайсы

- Имена — из бизнес-домена (`user`, `roll-dice`, `login`), не из техники (`components`, `utils`).
- Целевое состояние — **zero coupling** (независимы от соседей) и **high cohesion** (основная масса
  кода предметной области — вместе).
- Правило публичного API: каждый слайс обязан иметь public API (см. ниже).
- Количество не ограничено; слайс — инструмент навигации и изоляции.

### Slice groups — группировка слайсов

Не обязательная надстройка: когда слайсов много и плоский список трудно читать, близкие слайсы
складывают в папку-группу (`entities/payment/{invoice,receipt,transaction}`,
`pages/order/ {list,detail,create}`). Группа **не** является слайсом: у неё нет сегментов и
`index.ts`, правила зависимостей слайсов не меняются, общий код в группу класть нельзя. Заводить,
когда есть очевидный критерий группировки и слайсов заметно много; не заводить, если 2–3 слайса или
критерий надуман. В `features` группы применять осторожно: фичи режутся по use-case, а не по домену.

## Сегменты

Стандартные имена (группировка по технической природе):

| Сегмент  | Что сюда кладут                                             |
| -------- | ----------------------------------------------------------- |
| `ui`     | компоненты, отображение, стили, форматтеры дат/строк для UI |
| `model`  | схемы, интерфейсы, сторы, бизнес-логика                     |
| `api`    | запросы к бэкенду, типы/mapper-ы ответов                    |
| `lib`    | библиотечный код, нужный модулям слайса                     |
| `config` | конфиги и feature-flags                                     |

- В `app` и `shared` (слой без слайсов) можно заводить свои сегменты с именами-назначением. В
  слайсах остальных слоёв стандартных обычно хватает.
- Имя сегмента описывает **назначение**: `components`, `hooks`, `types`, `utils` — антипаттерн
  именования (см. code smell Desegmentation).
- **Внутри сегмента** структура свободна: можно плоско, можно папками-компонентами
  (`ui/head/Head.tsx`) — спека это не регламентирует; ограничение одно — держать навигацию и не
  плодить лишние уровни. Решение за проектом, а не за спекой.

## Public API (двери слайсов)

Каждый слайс (и каждый сегмент на слоях без слайсов) обязан иметь public API — контракт, реализуемый
как `index.ts` с re-export-ами:

```js
// pages/auth/index.js — канонический пример из спеки
export { LoginPage } from './ui/LoginPage'
export { RegisterPage } from './ui/RegisterPage'
```

Три цели хорошего контракта (цитата):

1. остальной код защищён от рефакторинга **внутри** слайса;
2. значимые изменения поведения слайса ломают его public API (а не тихо меняют потребителей);
3. наружу светится только нужный минимум.

Практические правила:

- `export *` в barrel — **плохая практика** (спека помечает как ❌): размывает контракт, случайно
  светит внутренности, мешает рефакторингу.
- Внутри слайса — только **относительные** импорты с полным путём; между слоями/слайсами — только
  **абсолютные** (алиасы). Это же главная защита от циклов `index.ts → модуль → index.ts`.
- `@x`-нотация (`entities/A/@x/B`) — кросс-импорт одной сущности в другую; применяется **только** на
  `entities` и минимально.
- Нет технической защиты обхода двери (auto-import может импортировать внутрь напрямую) — для
  контроля спека рекомендует архитектурный линтер **Steiger**.
- Подводные камни barrel: циклы, деградация tree-shaking в `shared/ui|lib`, замедление сборки на
  большом числе index-файлов. Меры: минимум дверей, не заводить `index` внутри сегментов при наличии
  `index` слайса, для `shared/ui|lib` — дверь на каждый компонент.

## Code smells (частые нарушения)

| Смell              | Признак                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Desegmentation     | группировка по техролям вместо доменов, generic-папки `components`, `utils`, `types`; смешение ui+model+api в одном файле |
| Cross-imports      | импорт между слайсами одного слоя в обход public API                                                                      |
| Excessive entities | раздутые/мусорные слайсы, бизнес-логика в `entities`, фичи-однострочники                                                  |
| God-component      | компонент-монолит → деление по секциям, хуки к владельцам                                                                 |
| Shared as dump     | `utils`/`helpers` без фокуса, бизнес-логика в `shared`                                                                    |

## Чек-лист «куда положить новый код»

1. Это запуск/глобальное — `app`. Иначе…
2. Это экран — слайс в `pages`. Если это **только** блок экрана: переиспользуется на ≥2 страницах
   или страница из нескольких крупных блоков — слайс в `widgets`, иначе оставьте в `pages`.
3. Это действие пользователя, переиспользуемое — слайс в `features`.
4. Это предмет/данные продукта — слайс в `entities`.
5. Это инфраструктура без бизнеса — сегмент `shared`.
6. Названия — бизнес-языком; сегменты — стандартными именами; внутрь слайса — относительные импорты,
   наружу — только через `index.ts`.
