# Паттерны ревью (code-review)

Секции = паттерны. Одна секция = один саб = один отчёт. Список расширяется добавлением секции — код
скилла не правится. Порядок проверок внутри секции — сверху вниз, он же приоритет.

Общие правила обоих файлов (единственный источник — формат находки и severity здесь, в других файлах
только ссылка):

- **Severity**: **блокер** (ломает сценарий/архитектуру, надо чинить), **замечание** (живут, но
  ухудшают базу), **идея** (BP-улучшение на потом). Уверенность: high (цитата + определение
  однозначны), med (контекст нужно уточнить), low (кандидат на обсуждение).
- Каждая находка: `файл:строка` (проверена чтением файла — нет проверки, нет находки) + короткая
  цитата + обоснование по определению секции + направление улучшения одной фразой.
- Google eng-practices (что смотреть в любом CL): design → functionality → complexity (особенно
  **over-engineering**: код обобщённее, чем нужно сейчас) → tests → naming → comments (**why**, не
  what) → consistency → documentation → every line → context. И главный принцип: **не принимать
  изменения, ухудшающие здоровье системы** — «мелкие» находки тоже копятся.

## 1. SOLID

**Определение.** SRP — у модуля одна причина изменяться. OCP — расширять поведение, не ломая
существующий код (новые случаи — новые ветки/модули, не правки старых в глубину). LSP — подтипы
подставимы вместо базовых без смены контракта. ISP — клиент не получает больше, чем использует
(толстые интерфейсы/экспорты). DIP — высокоуровневый код не зависит от деталей; детали подключаются
снаружи.

**Что проверяем.**

- SRP: модуль/функция делает больше одного дела (сборка DOM + расчёты + побочные эффекты +
  форматирование). Признаки: >~300 строк с разными ответственностями, функции-«свичи» на 100+ строк.
- OCP: `if/switch` по типам, который придётся править в N местах при добавлении варианта; правки
  существующих функций вместо добавления рядом (сверяй с `git log` — где чаще всего ломается).
- LSP/ISP: в модуль вывезено больше, чем нужно потребителям (экспорт «на всякий случай», толстые
  сигнатуры с флагами `boolean`); подкласс/обёртка меняет контракт базы (возвращает `null` там, где
  базовый бросал).
- DIP: высокоуровневый слой (`features`, `widgets`) импортирует низкоуровневые детали
  (`shared/three/*`, `cannon-es`) напрямую вместо того, что уже есть в `entities`/`shared` как
  абстракция.

**Не считать находкой.** SOLID-фанатизм: выделение абстракции «на будущую вторую реализацию» (это
уже YAGNI, см. секцию YAGNI); переупаковка простого кода в интерфейсы/классы без второй причины.
Google прямо: не обобщайся раньше времени — сначала доказанная нужда.

## 2. DRY

**Определение.** «Каждый фрагмент знания имеет единственное авторитетное представление» (The
Pragmatic Programmer). Дублируется не текст, а **знание**: правило, формат, константа, термин.
Независимые сущности, которые случайно похожи, дублированием не являются.

**Что проверяем.**

- Повторы: `grep`/поиск кусков ≥3–5 строк в одном файле и между слайсами (одинаковые форматтеры,
  обработчики, магические числа, строки-шаблоны вёрстки).
- Одно правило в двух местах: формат счёта/вероятности/локали дублируется в `entities` и `features`;
  CSS-правило скопировано в обе секции (в `mobile-table.css` особенно).
- Терминология: одна сущность названа по-разному (`model`/`skin`/`пресет` — проверить по `docs/` и
  коду: какое имя канонично).
- Дубль теста: два теста проверяют одно и то же с разными именами.

**Не считать находкой.** Намеренная дупликация двух независимо развивающихся кусков (правило трёх
ударов: <3 повторов — не дубль); копипаст 1–2 строк; похожесть без общего знания.

## 3. KISS

**Определение.** Простое решение понятно с чтения; сложность должна быть вынужденной (физика, 3D —
вынуждение), а не выбранной.

**Что проверяем.**

- Глубина вложенности >3 уровней (if → for → if → …); ранний `return` вместо обёрток.
- Длина функций: >~50 строк — кандидат на разбивку (не автоматический вердикт: сначала посмотри,
  действительно ли внутри несколько дел).
- «Умные» однострочники: цепочки тернарников, `?.`-каскады, вложенная деструктуризация,
  минус-инкременты в условиях — читается только автору.
- Флаги-параметры: `foo(a, true, false)` — вызывающий не понимает, что включено; bool-параметр
  меняет поведение.
- Преждевременная оптимизация микротасками (`requestAnimationFrame`-спагетти, ручная мемоизация без
  профилировки) — если не было измерения, это не оптимизация.

**Не считать находкой.** Сложность, обоснованная доменом (физика cannon-es, WebGL-матрицы); читаемый
и прямолинейный код даже в 100 строк; идиомы TS, знакомые команде.

## 4. YAGNI / over-engineering

**Определение.** «Ты это не понадобится» — не пиши функционал/абстракции, пока нужда не наступила.
Google в ревью называет это главным видом сложности: разработчики решают _гипотетические_ будущие
проблемы; будущее нужно решать, когда оно пришло и видна его форма.

**Что проверяем.**

- Мёртвый код: экспорт/функция/поле, используемое в одном месте — тесте; ветки `if`, куда никогда не
  заходят; «на будущее»: комментарии `TODO: потом`, параметры-заглушки, несуществующие режимы в
  конфигах.
- Абстракция с одной реализацией: интерфейс/базовый класс/стратегия с единственным наследником (или
  вообще без наследников), реестры/фабрики с одним участником.
- Фичи-призраки: опции в API виджета, которые не проброшены из UI; события, на которые никто не
  подписан (grep по именам).
- «Провизорная» гибкость: `extraConfig?`, `override?`, `hooks` — без единого потребителя в `src/`.

**Не считать находкой.** Реальная вторая реализация/потребитель уже есть в проекте (проверь grep-ом,
прежде чем помечать); расширение, которое явно заказано в задачах `tasks/` (mvp: если в
`tasks/mvp-2/*.md` есть требование — это не YAGNI).

## 5. FSD-границы (архитектура)

**Определение.** Слои проекта и правило «импорт только вниз» — источник правил:
`docs/ARCHITECTURE.md` (таблица «куда класть», приоритет: если правила спорят с привычкой — прав
Архив). FSD = feature-sliced design: `app → pages → widgets → features → entities`, `shared` внизу,
не зависит ни от кого.

**Что проверяем.**

- Импорты вверх/по горизонтали: `entities` импортирует из `features`/`widgets`; один `features/*` —
  из другого `features/*` (сквозные связи — через `entities`/`shared`); `shared` — вообще без
  импортов выше себя. Искать: `grep -rn "from '" src/<слой>` по запрещённым сочетаниям.
- Шпаргалка «куда класть» (ARCHITECTURE.md): новый экран не в `pages/`, действие не в `widgets/`,
  данные не в `features/` — сверить последние коммиты `git log --stat`.
- Коллизии CSS-классов/префиксов: правило проекта — префикс слайса (`model*`, `viewer*`, `mtable*`);
  глобальный CSS без префикса — замечание (см. границу «Глобальный CSS» в ARCHITECTURE.md).
- Скрытая связанность: модуль знает о существовании другого слоя через строковые константы (имена
  событий/классов), минуя импорт — тоже нарушение границы знания.

**Не считать находкой.** Легаси-решение, явно зафиксированное в ARCHITECTURE.md как «честная
граница» (например, DOM-код без тестов) — оно уже осознано и описано; не поднимать то, что документ
называет текущим компромиссом.

## 6. Тесты и BDD-связь

**Определение.** Тесты доказывают, что сломанное упадёт; приёмки задач (`tasks/mvp-2/*.md`, секции
«Приёмка») — это и есть спецификация поведения (BDD-дух: поведение из требований). Тесты — тоже код
на поддержку: их сложность и дубли считаются.

**Что проверяем.**

- Покрытие логики: чистая логика без DOM (`features/*`, `entities/*`, `shared/*` кроме
  three/physics) — есть ли рядом `*.test.ts`? Новая логика без теста — замечание. `grep -L` по парам
  функция/тест.
- Приёмка ↔ тест: взять приёмку из 2–3 последних задач и найти тест, который её проверяет; приёмка
  без теста (где это возможно чисто) — замечание с указанием, какой тест должен был бы покрыть.
- Тесты, которые не ломаются: смотри на `expect` — тест, который проверяет только «не бросило», или
  мокает всё, что тестируется, бесполезен; тест с закопанным в `expect` хардкодом того же значения,
  что и в коде, — хрупкий.
- Изоляция: общий мутабельный стейт между тестами (vitest `describe`-уровневые переменные),
  порядок-зависимость.
- Игнор/skip: `skip`/`todo`/`.only` — замечание, если их больше нуля.

**Не считать находкой.** Нетестированный DOM-код (в проекте осознанный выбор: UI покрывается
Playwright, а не Vitest — см. ARCHITECTURE.md); физика/3D без unit-тестов, если есть
Playwright-прогон (скрипты в `tmp/check/`); «не хватает интеграционного теста» без конкретного
сценария из приёмки.

## 7. Fail-fast и обработка ошибок

**Определение.** Ошибка должна всплывать там, где возникла, а не транслироваться в молчаливый
`null`/проглоченный `catch`. Границы системы валидируются; внутренние инварианты — через throw, а не
через «тихую» деградацию.

**Что проверяем.**

- Проглоченные ошибки: `catch {}` / `catch (e) {}` без репорта; `catch` с одним `console.warn` там,
  где функция продолжает работу с невалидным состоянием — grep `catch`.
- Тихая деградация вместо ошибки: `return null` / `return undefined` при невыполнении контракта
  (вызывающий получит `TypeError` дальше, причина потеряна).
- Молчаливые fallback-значения: `?? 0`, `?? []`, `|| 'default'` на входе, который по контракту
  обязан быть (внутренний API — пусть падает; публичный/пользовательский — валидируй явно).
- Валидация на границах: данные из `localStorage`/URL/`fetch` парсятся без проверки формы — смотри
  `features/ui-scale`, `localStorage`-читалки в `entities` (валидация при чтении настроек — эталон
  проекта).
- Ошибки UI: отказ загрузки/глушинки звука/WebGL-контекста — показано ли состояние пользователю, или
  он видит «ничего не происходит»?

**Не считать находкой.** `try/catch` вокруг кода с документированным fallback (звук при отсутствии
AudioContext — деградация осознанная и покрыта поведением); обработка ошибок в UI-слое, где throw
оставил бы юзера с белым экраном; `catch` с репортом в telemetry и осознанным продолжением.

## 8. Читаемость: имена, комментарии, магии

**Определение.** Имя достаточно длинное, чтобы объяснить сущность, и не длинное, чтобы мешать читать
(Google). Комментарии объясняют **почему**, а не **что**; если «что» непонятно — код надо упростить.
Документация класса/модуля описывает назначение и как пользоваться.

**Что проверяем.**

- Магические числа/строки: числа в формулах и UI-кодах без имени (`300`, `0.7`, `'750ms'`); дубль
  одного числа в двух местах — уже и DRY-находка. Константа в `entities`/`shared` — эталон.
- Имена: `tmp`, `data`, `res`, `item`, `handler2`, `x1/y1/z1` за пределами математики; сокращения,
  понятные только автору (`mdl`, `srv`); имя, врущее поведение (`isEnabled` → реально включает
  сайд-эффект?).
- Комментарии-пересказы (`// цикл по массиву`), устаревшие комментарии, противоречащие коду рядом,
  TODO без срока/задачи — grep `TODO|FIXME|HACK`.
- «Что» в комментарии vs «почему»: правило проекта — почему (история: костыли помечены с причиной,
  см. git blame).
- Единообразие: одно и то же действие называется везде одинаково (см. секцию DRY, терминология),
  стиль ошибок/логов единый.

**Не считать находкой.** Короткие имена в узкой области (цикл `i`, математические `t`, `n`);
комментарий-цитата из спеки/ссылка на issue; комментарии на русском, если весь слой на русском
(консистентность важнее языка); TODO, привязанный к задаче в `tasks/`.

## 9. Безопасность (базовая)

**Определение.** OWASP-база для фронтенда: не доверять пользовательскому вводу, не собирать HTML из
непроверенных данных, не хранить секреты в клиенте, не открывать XSS-векторов.

**Что проверяем.**

- `innerHTML`/`insertAdjacentHTML`/`document.write` с данными, которые пришли от пользователя или
  извне (внутренние константы — ок; имя комнаты/ввод пользователя — нет). grep
  `innerHTML|insertAdjacentHTML|dangerously`.
- `eval`, `new Function`, динамический `import()` по строке из URL/ввода.
- Секреты/токены в репозитории: grep по `token|secret|password|api_key` в `src/` и конфигах; `.env`
  не закоммичен (`.gitignore`).
- XSS через URL: значение из `location.search`/`hash`, попадающее в DOM без экранирования (парсеры
  пресетов/поделиться ссылкой — если появятся).
- Prototype pollution: `Object.assign(target, JSON.parse(userString))` без проверки ключа.

**Не считать находкой.** Отсутствие CSP (нет серверной части — CSP ставит хостинг, не проект);
экранирование в шаблонах, где весь вывод — константы разработчика; HTTPS/cookies (не используются);
«нет rate limiting» — вне клиента.

## 10. SDD: код ↔ спеки (условный)

**Определение.** Spec-driven development: код отвечает на спецификацию, а наоборот — не всегда.
Спеки проекта = `specs/` (задача 2.8) + приёмки `tasks/mvp-2/*.md`. Секция выполняется, только если
`specs/` существует; иначе — пропустить, отметить в summary.

**Что проверяем.**

- Расхождение: спека утверждает X, код делает Y (проверить по `specs/*.md` — контракты, форматы
  данных, состояния) — блокер или замечание по разнице.
- Код без спеки: сущность/формат появился в коде, но нигде не описан (grep ключевых `interface|type`
  — объявлены ли в спеках или хотя бы в `docs/`).
- Спека без кода: обещанное в спеке не реализовано — замечание «обещание висит».

**Не считать находкой.** Спека явно помечена «черновик/не реализовано»; расхождение, зафиксированное
в спеке как «известное отклонение»; отсутствие `specs/` (это не находка, а факт — одна строка в
summary).
