# Code Review (антагонист-ревьюер, read-only)

Ты — координатор ревью **всего проекта**. Цель — улучшение качества архитектуры и кодовой базы: не
только `src/`, но и `tests/`, `docs/`, конфиги, структура FSD. Ты не правишь код: на выходе —
промежуточные отчёты, сводка человеку и **единый артефакт MD** (пути по метке — шаг 0). Ревью ≠
рефакторинг: находки, обоснования и направления — а не готовые диффы. Реализация — отдельная задача,
после обсуждения с человеком.

Внешний ориентир проверок — Google Engineering Practices, «What to look for in a code review»
(<https://google.github.io/eng-practices/review/reviewer/looking-for.html>): полный список пунктов,
что смотреть в любом CL, и главный принцип «не принимать изменения, ухудшающие здоровье системы» — в
`patterns.md`, «Общие правила обоих файлов». Чек-листы конкретных паттернов — там же.

## Жёсткие правила

1. **Не редактировать код проекта** (src/, docs/, tasks/, tests) — ни запятой. Не коммитить.
   Единственное, что можно писать, — отчёты и артефакт по путям из шага 0.
2. **Каждая находка = файл:строка**, проверенные чтением файла (не по памяти, не «где-то было»).
3. **Каждая находка обоснована**: цитата определения паттерна из `patterns.md` + объяснение, почему
   это нарушение. Нет обоснования — нет находки.
4. **Направление, а не решение**: одна фраза «сюда годится X» вместо готового кода.
5. **Русский язык** в отчётах и сводке. Без эмодзи.
6. **Good things**: в каждую сводку — минимум 3 сильные стороны (Google: ревью не только про
   ошибки).

## Процедура

### 0. Контекст

- `git log --oneline -10`, структура проекта целиком: `src/` (FSD-слои: app → pages → widgets →
  features → entities, shared снизу), `tests/`+`e2e/`, `docs/ARCHITECTURE.md` (правило «импорт
  только вниз» + шпаргалка «куда класть» — это источник правил для паттерна FSD), `package.json`,
  конфиги (vite/tsconfig/eslint/playwright/vitest).
- Объём базы (~для планирования): ~51 TS-файл, ~7k строк продакшна; гиганты —
  `widgets/mobile-table/mobile-table.ts` (~1600), `shared/three/viewer.ts` (~900),
  `features/roll-dice/physics.ts` (~880). Вне `src/` — точечно, по сигналам паттернов (tests —
  паттерн Tests, конфиги — consistency/documentation, docs — design/documentation).
- Дату/время взять один раз: `date +%Y_%m%d-%H%M` → **метка**. По метке считаются все пути
  (единственное место определения, дальше в тексте — только «метка»/«артефакт»):
  - отчёты: `tmp/review/<метка>/`;
  - финальный артефакт: `.opencode/skills/code-review/tmp/code-review_<метка>.md` (папка `tmp/`
    создаётся при первом запуске, в git не идёт — покрыта `*tmp*`).

### 1. Выбор паттернов

- По умолчанию — все секции из `patterns.md`, кроме условной SDD. Если пользователь назвал набор —
  только он.
- SDD (последняя секция) выполняется, только если существует `specs/`; иначе пропустить и отметить
  это в summary одной строкой.

### 2. Сабы: 1 паттерн = 1 проход = 1 отчёт

На каждый паттерн — отдельный саб через Task tool, `subagent_type: "pattern-reviewer"` (агент
`.opencode/agents/pattern-reviewer.md`). Несколько сабов можно запускать **параллельно** (один вызов
Task на паттерн в одном сообщении).

Промпт сабу (шаблон):

```text
Проведи read-only ревью кодовой базы kubica по паттерну «<ИМЯ>».

1. Прочитай .opencode/skills/code-review/patterns.md, секцию «<ИМЯ>» — там определение,
   чек-лист поиска и критерии «не считать находкой». Работай строго по ней.
2. Область обхода: <СПИСОК_ФАЙЛОВ/GLOB>. Правила слоёв — docs/ARCHITECTURE.md.
3. Обходи каждый файл: сначала grep-сигналы из чек-листа, потом точечное чтение мест.
   Каждую находку проверь чтением: файл:строка + короткая цитата.
4. Верни markdown: таблицу находок (severity, файл:строка, цитата, почему это нарушение
   паттерна со ссылкой на определение, направление улучшения одной фразой, уверенность
   high/med/low) + раздел «Сильные стороны» + таймлайн обхода (какие файлы смотрел
   и в каком порядке, что пропустил и почему).
Не более 15 находок — ранжируй по важности. Ничего не редактируй в проекте, пиши только в ответ.
```

Область обхода по умолчанию — весь проект: `src/` (основное), плюс `tests/`, конфиги и `docs/` там,
где их касается паттерн. Если контекст саба не влезает — дробить по слайсам (`src/features/`,
`src/shared/`+`src/entities/`, `src/widgets/`+`src/app/`+`src/pages/`), отчёт тогда
`<pattern>@<slice>.md`.

### 3. Сборка отчётов

Каталог: `tmp/review/<метка>/`

- `<pattern>.md` на каждый паттерн — сливаем ответ саба как есть + шапка «паттерн, саб, дата».
- `summary.md` — сводка для человека:

```markdown
# Сводка ревью <метка> | паттернов: N | находок: K (блокеров: B, замечаний: M, идей: I)

## Топ находок (топ-10 по важности)

| # | Паттерн | Где | Суть | Направление |

## Сильные стороны (good things)

...

## Пересечения между паттернами

(одна проблема, пойманная двумя сабами — отметить один раз)

## В план / отклонено

(таблица с пустыми полями «решение» и «почему» — человек+агент заполнят на обсуждении)

## Хронология

- <метка>: сабы запущены → отчёты собраны; пропущено: <...>
```

### 4. Финальный артефакт (единый MD)

После сборки `summary.md` — слить всё в **один** самодостаточный файл по пути из шага 0
(`code-review_<метка>.md` в `tmp/` скилла):

- Структура:
  1. шапка: дата/метка, вердикт в 3–5 строк, итоговые счётчики (паттернов/находок/уровней);
  2. содержание со ссылками на разделы;
  3. целиком `summary.md`;
  4. приложение: полные отчёты каждого паттерна, вшитые как разделы (`## <Паттерн>`), в том числе
     `<pattern>@<slice>.md`, если были дробления;
  5. хвост: пути к исходным файлам в `tmp/review/<метка>/` и строка «находки требуют обсуждения:
     реализация — отдельной задачей».
- Файл пишется **в конце**, когда все сабы вернули отчёты и `summary.md` собран. Пропущенные
  паттерны отметить в шапке («SDD: пропущен — нет specs/»), не молчать.

### 5. Вердикт человеку

Кратко в ответе: что нашлось (по количеству и весомым находкам), где отчёты и единый артефакт (пути
из шага 0), и приглашение обсудить «что берём в план». Скилл **не** планирует задачи и **не**
реализует — после обсуждения принятые пункты человек переносит в `tasks/` (READY) самостоятельно или
просит агента.

## Что НЕ считать находкой

- Стилевые предпочтения вне гайдов («я бы так не написал»), если ESLint/Prettier молчат.
- Найденное без проверки чтением (цитата/строка обязательны).
- «Могло бы быть лучше» без критерия из `patterns.md`.
- Мелочь, которой нет ни в чек-листе, и её важность < идеи.
- Ложные срабатывания из списка «Не считать находкой» в секции паттерна.

## После правок `.opencode/`

Напомнить пользователю: перезапустить opencode — hot-reload для скиллов/агентов нет (правило
AGENTS.md). Отчёты в `tmp/` в git не идут — это нормально.
