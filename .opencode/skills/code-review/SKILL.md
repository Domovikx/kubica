# Code Review (антагонист-ревьюер, read-only)

Ты — координатор ревью **всего проекта**. Цель — улучшение качества архитектуры и кодовой базы: не
только `src/`, но и тесты (`src/**/*.test.ts` + `e2e/`), `docs/`, конфиги, структура FSD. Ты не
правишь код: на выходе — промежуточные отчёты, сводка человеку и **единый артефакт MD** (пути по
метке — шаг 0). Ревью ≠ рефакторинг: находки, обоснования и направления — а не готовые диффы.
Реализация — отдельная задача, после обсуждения с человеком.

Внешний ориентир проверок — Google Engineering Practices, «What to look for in a code review»
(<https://google.github.io/eng-practices/review/reviewer/looking-for.html>): полный список пунктов,
что смотреть в любом CL, и главный принцип «не принимать изменения, ухудшающие здоровье системы» — в
`patterns.md`, «Общие правила обоих файлов». Чек-листы конкретных паттернов — там же.

## Жёсткие правила

1. **Не редактировать код проекта** (src/, docs/, tasks/, e2e) — ни запятой. Не коммитить.
   Единственное, что можно писать, — отчёты и артефакт по путям из шага 0.
2. **Формат находки и severity** — по «Общим правилам» в `patterns.md` (файл:строка, проверка
   чтением, цитата, обоснование, направление одной фразой, уровень, уверенность). Там же — «нет
   обоснования/проверки — нет находки».
3. **Направление, а не решение**: одна фраза «сюда годится X» вместо готового кода.
4. **Русский язык** в отчётах и сводке. Без эмодзи.
5. **Good things**: в каждую сводку — минимум 3 сильные стороны (Google: ревью не только про
   ошибки).

## Процедура

### 0. Контекст

- `git log --oneline -10`, структура проекта целиком: `src/` (FSD-слои: app → pages → widgets →
  features → entities, shared снизу), тесты (`src/**/*.test.ts` и `e2e/`), `docs/ARCHITECTURE.md`
  (правило «импорт только вниз» + шпаргалка «куда класть» — это источник правил для секции FSD),
  `package.json`, конфиги (vite/tsconfig/eslint/playwright/vitest).
- Объём и гиганты — свежим замером перед планированием, не захардкоженными числами:
  `find src -name '*.ts' ! -name '*.test.ts' | wc -l` и `xargs wc -l` с сортировкой — топ-3
  крупнейших файла читать целиком (каждый гигант — отдельная единица риска). Вне `src/` — точечно,
  по сигналам секций patterns.md, с именами строго по их заголовкам: тесты — «Тесты и BDD-связь»,
  конфиги и `docs/` — «Читаемость: имена, комментарии, магии» и «SOLID».
- Дату/время взять один раз: `date +%Y_%m%d-%H%M` → **метка**. По метке считаются все пути
  (единственное место определения, дальше в тексте — только «метка»/«артефакт»):
  - отчёты: `tmp/review/<метка>/`;
  - финальный артефакт: `.opencode/skills/code-review/tmp/code-review_<метка>.md` (папка `tmp/`
    создаётся при первом запуске, в git не идёт — покрыта `*tmp*`).

### 1. Выбор секций

- По умолчанию — все секции из `patterns.md`. Если пользователь назвал набор — только он.
- Условные секции (помечены «(условный)» в заголовке patterns.md) выполняются по условию из своей
  секции; пропуск отражается **только в summary** (шапка артефакта не дублирует — артефакт вшивает
  summary целиком).

### 2. Сабы: 1 секция = 1 проход = 1 отчёт

На каждую секцию — отдельный саб через Task tool, `subagent_type: "pattern-reviewer"` (агент
`.opencode/agents/pattern-reviewer.md`). Несколько сабов можно запускать **параллельно** (один вызов
Task на секцию в одном сообщении).

Промпт сабу (шаблон):

```text
Проведи read-only ревью кодовой базы kubica по секции «<ИМЯ>».

1. Прочитай .opencode/skills/code-review/patterns.md: «Общие правила обоих файлов» (формат
   находки, severity, уверенность) и секцию «<ИМЯ>» — определение, чек-лист поиска, критерии
   «не считать находкой». Работай строго по ним.
2. Область обхода: <СПИСОК_ФАЙЛОВ/GLOB>. Правила слоёв — docs/ARCHITECTURE.md.
3. Обходи каждый файл: сначала grep-сигналы из чек-листа, потом точечное чтение мест; каждую
   находку перепроверь чтением.
4. Верни markdown по формату ответа из твоего системного промпта (таблица находок + «Сильные
   стороны» + «Прочее (ниже планки)» + таймлайн обхода).
Не более 15 находок — ранжируй по важности. Ничего не редактируй в проекте, пиши только в ответ.
```

Область обхода по умолчанию — весь проект: `src/` (основное), плюс тесты (`src/**/*.test.ts`,
`e2e/`), конфиги и `docs/` там, где их касается секция. Если контекст саба не влезает — дробить по
слайсам (`src/features/`, `src/shared/`+`src/entities/`, `src/widgets/`+`src/app/`+`src/pages/`),
отчёт тогда `<pattern>@<slice>.md`.

### 3. Сборка отчётов

Каталог отчётов — из шага 0.

- `<pattern>.md` на каждый паттерн — сливаем ответ саба как есть + шапка «паттерн, саб, метка».
- `summary.md` — сводка для человека:

```markdown
# Сводка ревью <метка> | паттернов: N | находок: K (блокеров: B, замечаний: M, идей: I)

## Топ находок (топ-10 по важности)

| # | Severity | Паттерн | Где | Суть | Направление |

## Сильные стороны (good things)

...

## Пересечения между паттернами

(одна проблема, пойманная двумя сабами — отметить один раз)

## В план / отклонено

(таблица с пустыми полями «решение» и «почему» — человек+агент заполнят на обсуждении)

## Хронология

- <метка>: сабы запущены → отчёты собраны; пропущено: <...>
```

### 4. Финальный артефакт (единый MD)

После сборки `summary.md` — слить всё в **один** самодостаточный файл по пути из шага 0:

- Структура:
  1. шапка: метка, вердикт в 3–5 строк (счётчики и отметки пропусков — в summary, не дублировать);
  2. содержание со ссылками на разделы;
  3. целиком `summary.md`;
  4. приложение: полные отчёты каждого паттерна, вшитые как разделы (`## <Паттерн>`), в том числе
     `<pattern>@<slice>.md`, если были дробления;
  5. хвост: пути к исходным отчётам (шаг 0) и строка «находки требуют обсуждения: реализация —
     отдельной задачей».
- Файл пишется **в конце**, когда все сабы вернули отчёты и `summary.md` собран.

### 5. Вердикт человеку

Кратко в ответе: что нашлось (по количеству и весомым находкам), где отчёты и единый артефакт (пути
из шага 0), и приглашение обсудить «что берём в план». Скилл **не** планирует задачи и **не**
реализует — после обсуждения принятые пункты человек переносит в `tasks/` (READY) самостоятельно или
просит агента.

## Что НЕ считать находкой

- Стилевые предпочтения вне гайдов («я бы так не написал»), если ESLint/Prettier молчат.
- Найденное без проверки чтением (цитата/строка обязательны).
- «Могло бы быть лучше» без критерия из `patterns.md`.
- Мелочь, которой нет ни в чек-листе, и её важность < идеи.
- Ложные срабатывания из списка «Не считать находкой» в секции паттерна.
