# Часть A. Канон FSD и конвенции kubica

## Канон (упрощённо)

Слои снизу вверх: `shared → entities → features → widgets → pages → app` (в спеке есть ещё
deprecated `processes`; в kubica все 6 слоёв объявлены, в `widgets` — самодостаточные оверлеи
страницы (drawer/sheet/musicCard), разнесение 2026-10-12, см. «Обоснование структуры» ниже). Импорт
— только на слой строго ниже. `shared` и `app` — слои без слайсов (только сегменты). Слайсы —
независимы (zero coupling) и когезивны (high cohesion). Стандартные сегменты слайса: `ui`, `api`,
`model`, `lib`, `config`.

### Import rule on layers

- Файл слайса импортирует другие слайсы **только со слоёв строго ниже**.
- Запрещены импорты вверх и между слайсами одного слоя. Легитимные связи сущностей — `@x`-нотация
  только на `entities` (в kubica не используется; общение компонентов — через `features/`-стор).

### Public API (barrel `index.ts`)

- Каждый слайс и слой-без-слайсов обязан иметь public API — контракт, защищающий внутреннюю
  структуру от внешних импортов.
- Экспортировать только нужный минимум. **`export *` запрещён** — размывает контракт и ломает
  рефакторинг.
- Внутри слайса — относительные пути с полным путём; между слайсами — абсолютные (`@/`). Импорт из
  слайса в его же `index.ts` → цикл.
- `shared/ui` и `shared/lib` — коллекции несвязанных вещей: одна дверь на весь сегмент тянет всё в
  бандл. Норма: `index.ts` на каждую библиотеку/компонент.
- В слайсах не плодить `index` внутри сегментов без нужды: `features/x/index.ts` достаточно.

### Антипаттерны (официальные code smells)

- **Desegmentation** — слой/слайс схлопнут в один сегмент или в корень; смешение ui+model+api.
- **Cross-imports** — импорты между слайсами одного слоя в обход public API.
- **Excessive entities** — раздутые слайсы; «мусорные» слайсы. Не каждая вещь — feature/entity:
  признак нужды — переиспользование и понятность новичку по списку слайсов.
- **God-component** — компонент-монолит → деление по секциям, хуки к владельцам.
- **Shared как дамп** — `utils/`/`helpers/` без фокуса; в `shared` каждая библиотека — одна сфера +
  README.

## Обоснование структуры (FSD v2.1: почему так)

Источники — действующая в 2026 спека FSD v2.1 на <https://feature-sliced.design>: Layers
(<https://feature-sliced.design/docs/reference/layers>), Slices and segments
(<https://feature-sliced.design/docs/reference/slices-segments>), пример Auth
(<https://feature-sliced.design/docs/guides/examples/auth>), code smell Desegmentation
(<https://feature-sliced.design/docs/guides/issues/desegmented>). Ресёрч и решения — 2026-10-12
(владелец: «обоснование и дока»).

1. **Композиция стола — в `pages/HomePage`, самодостаточные оверлеи — в `widgets` (разнесение
   2026-10-12).** Спека, Layers → Widgets: «If a block of UI makes up most of the interesting
   content on a page, and is never reused, it should not be a widget, and instead it should be
   placed directly inside that page». `HomePage` был 12-строчной обёрткой, `MobileTable` — 100 %
   содержимого единственной страницы, поэтому композиция экрана (контейнер, шапка/фут/хинт, движок,
   `selectPhase`) осталась в странице (спека, Layers: «You don't have to use every layer … only add
   them if it brings value»). Решение владельца 2026-10-12 (метод снизу вверх от `shared`): **панель
   настроек (`widgets/drawer`), шторка пресетов (`widgets/sheet`), карточка музыки
   (`widgets/musicCard`)** — между ними zero coupling (прямых импортов нет, связь только через
   features-стейт и shared-кит), у каждого свой стейт-контракт — это слайсы виджета, а не содержимое
   страницы; общий кит (`OverlayHead`, `overlay.stylex`, `mt.stylex`) — в `shared/ui` (презентация
   без бизнеса, общая для трёх слой-единиц). **Критерий новых наполнений `widgets`:** блок
   переиспользуется на ≥2 страницах ИЛИ это самостоятельный оверлей, не сращённый с композицией
   экрана (напр. viewer-grid).
2. **Сегменты `ui/model/lib` внутри `pages/HomePage`.** Спека, Slices and segments: стандартные
   сегменты `ui/api/model/lib/config` — группировка «по технической природе»; «Inside a slice, the
   code could be organized in any way that you want» — контракт держит public API слайса
   (`index.ts`). Пример Auth: `pages/login/{ui/LoginPage.tsx, index.ts}` — ровно наш формат
   (папка-слайс + сегменты + дверь).
3. **Папки компонентов внутри сегмента — атомы, не под-слайсы.** Группировка 2026-10-12: компонент +
   всё, что относится только к нему, — в папку (`pages/HomePage/ui/Head/`, `ui/Watermark/` —
   компонент + его хуки/stylex; в `widgets/sheet/` — секции, `Chip`, `useChipHold`), без
   промежуточного `components/`; одиночные компоненты — плоско в корне `ui/`. Это группировка ВНУТРИ
   сегмента («Inside a slice, the code could be organized in any way that you want»), а не
   под-слайсы: кросс-импорты папок одного слайса — относительные внутри одного сегмента; между
   слайсами (в т.ч. `widgets/sheet → widgets/drawer` — не бывает) и к киту — только в двери слоёв.
   Запрет оставался на доменные под-слайсы с общими сквозными импортами. Кит оверлея (`OverlayHead`,
   `overlay.stylex`, `mt.stylex`) после разнесения — в `shared/ui`: один на три widgets-слайса,
   презентация без бизнеса — единственный легальный дом.
4. **Почему плоские entities/features допустимы.** Внутри слайса организация свободна (цитата выше);
   плоскость — решение владельца (KISS/YAGNI, 2026-10-12: файлы в корень слайса, без
   `dieModel/model/…`). Smell Desegmentation бьёт по generic-папкам и именам вроде
   `components/hooks/utils` («bad segment names») и по смешению доменов в одном файле — не по
   отсутствию сегментов у слайса из 3–4 файлов; steiger `fsd/no-segmentless-slices` off — осознанная
   оговорка с комментарием в `steiger.config.ts`.
5. **История структуры стола:** сегменты + папки компонентов с промежуточным `components/`
   (`mobileTable/ui/components/…`, 5 уровней) — владелец: «избыточная вложенность»; полный flatten
   (42 файла в корне слоя, 3 уровня) — владелец: «ужас»; плоские сегменты (3–4 уровня) — компромисс
   глубины. **Финальное решение 2026-10-12:** папки компонентов БЕЗ `components/` — компонент + его
   атомы (`widgets/drawer/Drawer.tsx`, `pages/HomePage/ui/Head/Head.tsx`, 4 уровня), одиночные
   компоненты плоско в корне `ui/`; затем разнесение по слоям (п. 1): оверлеи → `widgets/`, кит →
   `shared/ui`, хуки/селекторы/форматтеры → владельцам стейта.

## Конвенции kubica (дополняют канон)

- Слои: `app, pages, widgets, features, entities, shared` — все 6 объявлены всегда; `widgets`
  содержит слайсы `drawer/sheet/musicCard` (разнесение 2026-10-12; см. «Обоснование структуры»).
  Шпаргалка «куда класть» — `docs/ARCHITECTURE.md` §«Куда класть новый код».
- **Двери**: у каждого слоя `index.ts` (`@/features`, `@/entities`, `@/pages`, `@/widgets`,
  `@/shared`, `@/app`); у слайсов со значимым объёмом — своя (`features/tableRoll/index.ts`,
  `widgets/sheet/index.ts`, `pages/HomePage/index.ts`); **у каждой папки-компонента — своя**
  (`ui/Head/index.ts`, `widgets/drawer/index.ts`): потребитель импортирует папку, а не файл
  (`./Head`, а не `./Head/Head`) — импорты без шума. Двери НЕ плодятся в служебных сегментах
  (`model/`, `ui/` целиком) и внутренних служебных папках (`api/mocks/`) — там дверь сегмента/слайса
  выше. Внутри слайса — относительные импорты, без лишних barrel'ов; снаружи — в дверь. Прямые
  импорты внутренностей чужого слайса — нарушение (см. Часть C.2).
- Компоненты страницы общаются между собой только через `features/`-стор; общий доступ к стору/хукам
  приложения — `app/store`, `app/hooks` (осознанные исключения dep-cruiser и steiger); хуки в
  слайсах `features` диспатчат через `useDispatch` из `react-redux` напрямую — импорт `@/app` из
  features замыкает цикл `store → features-дверь → хук → store`.
- Хуки-владельцы: хук живёт рядом с владельцем стейта/домена: `widgets/sheet/useChipHold`,
  `pages/HomePage/ui/Head/useFitHeadStar`, `ui/Watermark/useWatermarkFit`; `useToast` (мотор
  контейнера `MobileTable`) — в корне `ui/`; `useDirtyPanel` — `features/tableUi`, `useSoundToggle`
  — `features/sound` (владельцы диспатча); `useTableEngine`, движок, экранный `selectPhase` —
  `model/`; селекторы стейта — `features/*/selectors.ts` и `entities/rollHistory/selectors.ts`
  (рядом с редьюсером, структурная типизация вместо RootState); форматтеры — у владельца типа
  (`features/tableSetup/format.ts`, `entities/rollHistory/format.ts`). Сегмент `lib/` упразднён.
- Именование: `.tsx`-компоненты PascalCase, стили `<база>.stylex.ts`, утилиты `<база>.utils.ts`,
  папки camelCase; DOM-маркеры `.mtable*`, `data-testid`, `data-phase` — контракты, не трогать.
- Механика: `npm run lint:arch` (dep-cruiser: импорты только вниз, no-circular), `npm run lint:fsd`
  (steiger + `@feature-sliced/steiger-plugin`, исключения — `steiger.config.ts` с комментариями).

## Практика композиции (React)

- Контейнер владеет данными/состоянием, презентация — чистые пропсы; хук — владелец своей доменной
  логики.
- Большие секции экрана — в подкомпоненты той же папки; `index.ts` экспортирует только
  верхнеуровневый компонент.
- Композиция через children/slots предпочтительнее леса пропсов-флагов; повторяющиеся паттерны —
  compound-компоненты (как `Sheet` + секции).
- State-визуал — глобальные правила styles.css; stylex — модульный, state через классы.

# Часть B. Процесс ревью (координатор, read-only)

Ты — координатор FSD-ревью **проекта kubica**. Цель — границы слоёв/слайсов, public API, здоровье
структуры, композиция React. Ты не правишь код: на выходе — промежуточные отчёты, сводка и **единый
артефакт MD** (пути по метке — шаг 0). Ревью ≠ рефакторинг. Реализация — отдельная задача после
обсуждения. Ориентир: Google Engineering Practices — «не принимать изменения, ухудшающие здоровье
системы».

## Жёсткие правила

1. **Не редактировать код проекта** (src/, docs/, tasks/, e2e, конфиги) — ни запятой. Не коммитить.
   Писать можно только отчёты/артефакт по путям шага 0.
2. **Формат находки и severity** — «Общие правила» в Части C (файл:строка, цитата, обоснование,
   направление одной фразой, severity, уверенность). Нет проверки чтением — нет находки.
3. **Направление, а не решение**: одна фраза «сюда годится X».
4. **Русский язык**, без эмодзи.
5. **Good things**: в каждую сводку — минимум 3 сильные стороны архитектуры.

## Процедура

### 0. Контекст

- `git log --oneline -10`; структура `src/` целиком; топ-5 крупнейших `.ts/.tsx` свежим замером
  (`find src -name '*.ts*' ! -name '*.test.*' | xargs wc -l | sort -rn`); `docs/ARCHITECTURE.md`;
  `package.json`, `.dependency-cruiser.mjs`, `steiger.config.ts`.
- Механика (один раз, до планирования сабов) — запустить и вшить вывод в контекст сабов:
  - `npm run lint:arch` (dep-cruiser);
  - `npm run lint:fsd` (steiger). Ошибки механики — сигналы сабам для перепроверки чтением;
    механические находки не дублировать вручную, если секция не про механику. Отдельно перечисли
    задокументированные исключения `steiger.config.ts`/depcruiser — конвенции, а не находки.
- Дату/время один раз: `date +%Y_%m%d-%H%M` → **метка**:
  - отчёты: `tmp/review/fsd-<метка>/`;
  - артефакт: `.opencode/skills/fsd-review/tmp/fsd-review_<метка>.md` (`tmp/` в git не идёт).

### 1. Секции

Все 5 из Части C: «Слои и импорты», «Public API и barrel», «Слайсы: границы и здоровье», «Компоненты
и композиция React», «Сегменты и именование». Если пользователь назвал набор — только он.

### 2. Сабы: 1 секция = 1 проход = 1 отчёт

На каждую секцию — отдельный саб через Task tool, `subagent_type: "fsd-reviewer"` (агент
`.opencode/agents/fsd-reviewer.md`; если агент не подхватился — `explore` с инструкциями агента,
вставленными в промпт). Параллельно — несколько Task в одном сообщении.

Промпт сабу (шаблон):

```text
Проведи read-only FSD-ревью кодовой базы kubica по секции «<ИМЯ>».

1. Прочитай .opencode/skills/fsd-review/SKILL.md: Часть C — «Общие правила» + секцию «<ИМЯ>»
   (определение, чек-лист, «не считать находкой»). Канон/конвенции — Часть A того же файла.
   Работай строго по секции.
2. Область обхода: <СПИСОК_GLOB>. Слои — docs/ARCHITECTURE.md.
3. Механика (сигналы, перепроверь чтением): <вывод lint:arch и lint:fsd + список исключений
   конфигов>.
4. Обход: сначала grep-сигналы чек-листа, потом точечное чтение; каждую находку — чтением.
5. Верни markdown форматом ответа из твоего системного промпта (таблица + «Сильные стороны» +
   «Прочее (ниже планки)» + таймлайн). Не более 15 находок. Ничего не редактируй.
```

Если контекст саба не влезает — дробить по слоям (`src/pages+app`, `src/features`,
`src/entities+shared`), отчёт тогда `<section>@<slice>.md`.

### 3. Сборка отчётов

- `<section>.md` на каждую секцию — ответ саба + шапка «секция, саб, метка».
- `summary.md`:

```markdown
# Сводка FSD-ревью <метка> | секций: N | находок: K (блокеров: B, важно: V, замечаний: M, идей: I)

## Топ находок (топ-10 по важности)

| # | Severity | Секция | Где | Суть | Направление |

## Сильные стороны (good things)

...

## Пересечения между секциями

(одна проблема двумя сабами — отметить один раз)

## В план / отклонено

(таблица с пустыми полями «решение» и «почему»)

## Хронология

- <метка>: механика lint:arch/steiger прогнана; сабы → отчёты собраны; пропущено: <...>
```

### 4. Финальный артефакт (единый MD)

Всё в **один** самодостаточный файл по пути шага 0:

1. шапка: метка, вердикт 3–5 строк;
2. содержание;
3. целиком `summary.md`;
4. приложение: полные отчёты секций (`## <Секция>`, включая `@slice`-дробления);
5. хвост: пути к исходным отчётам + «находки требуют обсуждения: реализация — отдельной задачей».

Пишется в конце, когда все сабы вернулись и `summary.md` собрана.

### 5. Вердикт человеку

Кратко: что нашлось, где отчёты/артефакт, приглашение обсудить «что берём в план». Скилл **не**
планирует и **не** реализует — принятые пункты после обсуждения переносятся в `tasks/` (READY) по
просьбе.

## Что НЕ считать находкой

- Стилевые предпочтения вне гайдов, если ESLint/Prettier молчат.
- Найденное без проверки чтением.
- «Могло бы быть лучше» без критерия из секции.
- Мелочь ниже планки идеи.
- Ложные срабатывания из «не считать находкой» конкретной секции и задокументированные
  конвенции-исключения ( Часть A).

# Часть C. Секции ревью (чек-листы)

## Общие правила (формат находки)

- Severity: **блокер** (ломает границы/бандл/рефакторинг) → **важно** (архитектурный дрейф, риск
  копиться) → **замечание** (нарушение конвенции) → **идея** (направление улучшения).
- Уверенность: high / med / low. Нет обоснования или проверки чтением — нет находки.
- Обязательные поля: `файл:строка`, краткая цитата (1–2 строки), почему нарушение (по определению
  секции), направление одной фразой, severity, уверенность.
- Направление, а не готовый код/дифф. Ссылку на другую секцию не ставить — за другую секцию отвечает
  другой проход.
- Порог: не более 15 находок на секцию, ранжирование блокер → идея; шум ниже идеи — в «Прочее».

## 1. Слои и импорты

**Определение.** Слой — уровень ответственности
(`shared → entities → features → widgets → pages → app`). Импорт — только на слой строго ниже; в
обход — нарушение границы.

**Чек-лист.**

- Импорт вверх по слоям (тесты, `.css` и исключения dep-cruiser — не считать).
- Импорт между слайсами одного слоя (только `features/`-стор/`app/store|hooks` — осознанные
  исключения kubica).
- Обход public API слайса: прямой импорт внутрь чужого слайса (`pages/HomePage/ui/Head` вместо
  двери) — снаружи слайса через barrel/дверь.
- «Тихие» связи: импорт чужих типов/констант, side-effect импорты ради единой константы.
- `shared` тянет бизнес (импорт из `entities+`) или слоёв выше.

**Не считать находкой.** Внутрислайсовые относительные импорты; `app/(store|hooks)` из слайсов;
тесты; импорты css/ассетов; уже задокументированные исключения dep-cruiser/steiger.

## 2. Public API и barrel

**Определение.** Контракт слайса/папки — `index.ts` с минимумом экспортов; снаружи видно только его.
Нет контракта → структура слайса становится де-факто API.

**Чек-лист.**

- Слайс/папка-компонент без `index.ts` при использовании снаружи.
- `export *` в любом barrel'е.
- Barrel экспортирует внутренности (приватные типы/утилиты, «на будущее»).
- Лишние уровни barrel'ов (index в сегменте слайса при наличии index слайса; цепочки re-export ради
  одного имени).
- Цикл: модуль импортирует `../` (index) собственного слайса.
- shared-сегмент с одной дверью на всё (если появился) — тянет тяжёлое в бандл.

**Не считать находкой.** Двери слоёв и слайсов (`index.ts`) как barrel — конвенция kubica (см. часть
A); отсутствие вложенных barrel'ов внутри сегментов — тоже конвенция (прямые относительные импорты
внутри слайса).

## 3. Слайсы: границы и здоровье

**Определение.** Слайс — когезивная независимая единица. Дрейф: desegmentation, cross-imports,
excessive entities, god-slice, shared как дамп.

**Чек-лист.**

- Desegmentation: слой/слайс без сегментации, смешение ui+model+api в одном файле без нужды;
  несемантические имена сегментов (`components`, `hooks`, `utils` в корне слоя).
- Excessive entities: раздутые слайсы (гиганты), логика фич в `entities`, «мусорные» слайсы, слайсы
  ради одного компонента.
- Shared-дамп: `utils/helpers` без фокуса; в shared — бизнес-логика.
- Дублирование структур между слайсами (копипаст слайса вместо переиспользования).
- Слайс, который нечем занять на верхних слоях (мёртвый слайс/сегмент — dep-cruiser orphans как
  сигнал, проверка чтением).

**Не считать находкой.** Один крупный, но цельный слайс (< порога гиганта); единственная страница —
не повод заводить processes/лишние слои сверх канона; задокументированный техдолг сегментации
(steiger `no-segmentless-slices` off) — не дублировать, но оценивать когезивность.

## 4. Компоненты и композиция React

**Определение.** Размещение ответственностей в UI: контейнер/презентация, хук-владелец, размер,
пропсы, дублирование.

**Чек-лист.**

- Компонент-гигант (>~250 строк, несколько секций) без деления или с делением «просто так».
- Пропсы-флаги (boolean forests) вместо children/slots; лес условий в JSX без подкомпонентов.
- Хук-владелец не на месте: DOM/UI-хук в общих `hooks/`, бизнес-хук в компоненте, который им не
  владеет; дублирование хуков между папками.
- Дублирование UI-дерева (одна секция скопирована в два компонента вместо подкомпонента).
- Состояние из store, разогнанное в useState-дереве пропсов (и наоборот).
- Стили: не-stylex инлайн-логика там, где нужен stylex/state-класс; нарушение паттерна
  `stylex.props()` → `{...sx}` → `className={\`mtableMarker ${sx.className ?? ''}\`}`.

**Не считать находкой.** Маркеры контракта (`.mtable*`, `data-testid`, `data-phase`, `--ui-scale`);
«я бы так не написал» без критерия; state-визуал через глобальные правила styles.css — конвенция.

## 5. Сегменты и именование

**Определение.** Внутренняя структура слайса: сегменты `ui/api/model/lib/config`, имена
файлов/папок, колокализация.

**Чек-лист.**

- Код вне стандартных сегментов в слайсе (всё в корне слайса) — desegmentation (см. оговорку в
  секции 3 про задокументированный техдолг).
- Семантика не соответствует сегменту (бизнес-логика в `ui`, UI в `model`).
- Именование: не PascalCase для `.tsx`-компонентов, не camelCase для папок, не `<база>.stylex.ts` /
  `<база>.utils.ts`.
- Тесты мимо сегментов (не рядом с модулем, `src/__tests__`-свалка).

**Не считать находкой.** Согласованные отступления проекта (плоские слайсы entities/features без
сегментов — `no-segmentless-slices` off, задокументировано; сегменты `pages/HomePage/{ui,model}` —
решение 2026-10-12; `app/store|hooks` — устоявшиеся имена; PascalCase-файлы компонентов — см.
конвенцию именования).
