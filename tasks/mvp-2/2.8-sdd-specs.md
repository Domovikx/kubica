# 2.8 Минимальный SDD: папка спек = тудушки = отчёт сделанного (с датами)

Статус: READY

## Цель

Негде вести документ сделанных фич и идей. Нужен **минимальный SDD** (spec-driven development):
отдельная папка, куда можно кидать микро-идеи одним движением, они оформляются в микро-спеки и же
являются отчётом «что и когда сделали». Обязательна **тайминг-привязка** (даты смены статусов +
история переделок): мы делаем → передумываем → переделываем, и терять эти витки нельзя.

## Контекст (ресёрч: SDD на минималках)

- SDD (GitHub Spec Kit, `github/spec-kit/docs/concepts/sdd.md`): спецификация — **single source of
  truth**, «what» до «how», спека — живой контракт, а не разовый документ; код
  генерируется/валидируется против спеки. Полный конвейер Spec Kit (constitution → specify → plan →
  tasks → implement) с CLI — **избыточен**, берём только суть: папка + шаблон + статусы с датами.
- Существующие уровни не заменяем, а связываем:
  - `docs/PLAN.md` — глобальный план срезов;
  - `tasks/` — очередь задач для агентов (READY→DOING→DONE);
  - `docs/*.md` (UX_ROLL, DICE_TRAY…) — крупные спеки доменов. Новое — **микро-уровень «фича»**:
    одна фича = один файл спеки, статус + даты.
- Быстрый сброс идей: паттерн «inbox → оформить позже» (как GTD): отдельный `_inbox.md` — одна
  строка = одна идея, чтобы накидывать без структуры.

## Требования

1. Папка `specs/` в корне (в git):
   - `README.md` — правила (2–3 экрана) + **реестр-таблица**: фича | статус | дата DONE |
     коммит/ссылка. Быстрый ответ «когда что сделали».
   - `_inbox.md` — сброс идей: строка вида
     `- 2026-10-04 — идея (когда оформлена — ссылка на спеку)`. Закидать идею ≤30 секунд, без
     шаблонов.
   - `_TEMPLATE.md` — шаблон микро-спеки.
2. Шаблон микро-спеки (одна фича):
   - **Статус с датами**: `IDEA (дата) → SPEC'D (дата) → DOING (дата) → DONE (дата)`.
   - **Что** (поведение, 3–10 строк) + **Приёмка** (проверяемые пункты).
   - **Реализация**: ссылки на файлы + коммит(ы) + дата DONE.
   - **История решений**: датированные строки переделок — старое НЕ удалять («2026-10-04: ряды
     рядами; 2026-10-05: передумали → сетка»).
3. Жизненный цикл (правило захвата):
   - идея → строка в `_inbox.md`;
   - начинаем делать → оформляем файл из шаблона, переносим строку из inbox (со ссылкой);
   - DONE → дата + коммит в спеку + строка в реестр `specs/README.md`;
   - передумали/переделали → новый блок в «Истории решений», спека не стирается, статус крутится
     заново с датой.
4. Связка с `tasks/`: задача указывает спеку, спека — задачу (в конце файла секция «Связи»).
   Дублировать содержимое задач в спеку нельзя.
5. Правило для агентов: короткий параграф в `AGENTS.md` — «фича не DONE, пока спека не обновлена
   (дата+коммит)»; агент при закрытии задачи обновляет спеку и реестр.
6. Без автоматизации на старте: никаких CLI/скриптов, только markdown. (Опционально позже:
   скрипт-чек, что реестр совпадает со спеками.)

## Приёмка

- Идей в `_inbox.md` можно накидать пачкой за минуту (одна строка каждая).
- По `specs/README.md` за 10 секунд видно: что сделано, когда (дата DONE), каким коммитом.
- Есть ≥1 спека с заполненной «Историей решений» — видно, что фичу переделывали и когда.
- Ни одна строка из inbox не теряется при оформлении в спеку (перенос, не копия).
- `npx tsc --noEmit`, eslint, `npm test` не задеты (только markdown); pre-commit хуки
  (prettier/markdownlint) проходят на новых файлах.

## Файлы

- `specs/README.md`, `specs/_inbox.md`, `specs/_TEMPLATE.md` — создать.
- `AGENTS.md` — параграф про обязательное обновление спеки при DONE.
- `tasks/README.md` — одна строка-связка со `specs/`.
