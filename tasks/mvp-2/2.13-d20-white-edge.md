# 2.13 d20: убрать белый цвет с двух рёбер (радиус скругления сохранить)

Статус: DONE

## Самоуточнение диагноза юзером (важно, не путать с 2.12!)

Первичные формулировки («убрать блик», «острое ребро») — **неверны**, юзер уточнил:

1. Это **не блик**: на d20 **2 ребра на ПРОТИВОПОЛОЖНЫХ сторонах покрашены в белый** — это реальный
   белый цвет в кубике (в меше/материале), а не световой отблеск.
2. Это **не острое ребро**: радиус скругления виден и **юзеру нравится** — **EDGE_R=1 сохранить,
   геометрию не трогать**.
3. Задача: убрать **именно белую краску** с этих двух рёбер — цвет должен стать как у остальных
   рёбер/тела. Больше ничего не менять.

(Задача 2.12 — исследование блика — осталась DONE со своим вердиктом; здесь новый, уточнённый
дефект: белый цвет, не шейдинг.)

## Что известно

- Геометрия: `tools/dice_set.scad` `EDGE_R = 1` — **не менять**.
- Окраска: пайплайн `tools/blender-stl-colorize-set.py` (STL → материал/цвет → GLB в
  `public/cad/set/d20.glb`). Подозрение №1 — там: фаска/ребро красится в белый либо назначается
  белый material на бандл этих рёбер. Симметрия (ровно 2 ребра, противоположные) намекает на
  закономерность в скрипте (выбор рёбер по оси/парности).
- Сцена: `src/shared/three/table.ts` — материал/свет общие для всех костей, белый на конкретных
  рёбрах — из меша, не из сцены (проверить: если снять Env/Lights — белое остаётся белым → цвет в
  материале).

## Что сделать

1. **Подтвердить визуально**: скриншоты d20 — какие рёбра белые (координаты/номера граней по
   сторонам), только ли они; остальные кости набора (d6/d8/d10/d12) — нет ли белых рёбер там тоже
   (если скрипт общий — возможно, дефект везде; тогда отметить, но чинить по факту согласования:
   юзер просил d20).
2. **Найти источник белого**:
   - `tools/blender-stl-colorize-set.py` — grep по белому/цветам (RGB 1,1,1 / 0xFFFFFF);
   - структура `public/cad/set/d20.glb`: материалы, кто какой бандл/полигоны держит (скрипт на three
     GLTFLoader в tmp/check/ или `npx @gltf-transform/cli inspect`, если пакет уже доступен — новых
     зависимостей не ставить);
   - воспроизвести логику colorize: как выбираются рёбра/грани под покраску.
3. **Фикс** (минимальный, без пересборки геометрии!):
   - если белый задаётся в colorize-скрипте — исправить цвет на цвет тела/границы (как у остальных
     рёбер) и пересобрать GLB (этап SCAD не нужен — геометрия та же; нужен только STL → colorize,
     либо перекраска готового GLB через Blender CLI python: замена материала/переназначение бандла);
   - если в GLB уже есть отдельный белый материал — перекрасить его (та же перекраска), не трогая
     меш;
   - после фикса: ребро выглядит как остальные (цвет тела/фаски), радиус в силе.
4. Если пайплайн пересборки/перекраски недоступен (нет Blender CLI) — честный блокер и точный план
   команд в отчёте; руками в three.js цвет не подменять (косметика в коде — не фикс корневой
   причины).

## Итог

**Источник белого** — `tools/blender-stl-colorize-set.py`, бокс-тест `is_pip` (цикл по
`digit_boxes`, ~строки 255–280): бокс цифры продлён ниже глифа (`lo = -half_v - size*0.35` для 6/9,
широкий `half_u` для двухзначных) и глубина `0.005 < depth < 0.4` — центроиды **5 тонких
слайвер-треугольников** (0.13×10.25 мм, глубина 0.005–0.018) **на вершине скругления** вдоль рёбер
(зона цифр 6 и 9 на противоположных гранях) попадали в бокс и красились в `D_pips` (белый).
Противоположная симметрия = парность 6/9. Только d20: `tmp/check/dice-white-scan.mjs` — на
d4/d6/d8/d10/d12 наклонённых пипс-треугольников 0.

**Фикс** — guard в `is_pip` (после прохождения бокса): `dev` — угол между нормалью треугольника и
нормалью бокс-грани. Пол пикса: `dev ≤ 3°`; стенка глифа (вертикальный рез): `dev ≥ 60°` — остаётся
пипсом; скругление (дефектные слайверы `dev = 5.9–10.6°`) — не пипс. Зазоры огромные: полы
`≤0.003°`, стены ровно `90°`.

  box-тест не тронут.
